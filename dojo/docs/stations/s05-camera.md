# S05 · 相机与打击感

> **练什么**：Camera2D 跟随 · 指数平滑 · 屏幕震动 · 顿帧 · 前瞻 · 相机边界
> **一句话**：同样的机制，加不加这些反馈，**是两个游戏**。
> **难度**：★★★☆☆（原理都很简单，难的是"感觉到差异"——所以本站把每个效果都做成了开关）

---

## 一、先玩一遍

这是一间 1800×1200 的手感实验室（比屏幕大，所以相机会真的动起来）。

**三种玩法**：

| 做什么 | 会看到什么 |
|---|---|
| `WASD` 撞向灰色的柱子 | 屏幕震动，强度取决于你的速度 |
| 走到**训练假人**旁边按 `J` | 顿帧 + 震屏 + 白闪「三件套」 |
| 走到**东北角**和**西南角**（蓝色菱形） | 相机会被边界卡住，**角色会偏离屏幕中心** |
| 鼠标滚轮 | 缩放 |

**左上角有五个开关，按 `1`~`5` 随时切换：**

| 键 | 关掉的东西 |
|---|---|
| `1` | 屏幕震动 |
| `2` | 顿帧 |
| `3` | 平滑跟随（关掉 = 相机直接贴住玩家） |
| `4` | 前瞻（相机会朝鼠标方向偏移） |
| `5` | 相机边界（关掉后相机会拍到关卡外面的黑区） |

> **全部关掉再玩一遍，然后把它们一个个打开。**
> 打击感这种东西，读代码是学不会的，必须手动开关几次建立起肌肉记忆。

地板上的点阵不是装饰 —— **没有参照物的话，相机移动你是看不出来的**。

## 二、核心概念一：指数平滑（别用 Lerp）

跟随相机最容易写错的一行是：

```csharp
// ❌ 错误写法
position = position.Lerp(target, 0.1f);

// ✅ 正确写法
position = position.Lerp(target, 1f - Mathf.Exp(-sharpness * delta));
```

**为什么第一个是错的**：`0.1f` 是"每帧消掉 10% 的差距"。
帧率翻倍，每秒就多消一倍的差距 —— 于是**30fps 和 144fps 下的跟随手感完全不同**。
你可能在开发机上调得很舒服，玩家在别的机器上感觉相机在拖后腿。

**为什么第二个是对的**：`1 - e^(-k·dt)` 的含义是"每秒消掉 `1 - e^-k` 的比例"，
它把 `dt` 也算进去了，所以与帧率无关。`k` 越大越紧跟。

**顺便说一个反直觉的点**：`k = 9` 看起来很大（每秒消掉 99.99%），
但因为是指数逼近，"剩余差距"永远在按比例缩小，实际手感是
**紧跟 + 一点点回弹** —— 这正是想要的。真正要紧跟就该用 `k = 20`，
真正要"慢悠悠"就用 `k = 4`。

> Godot 的 `Camera2D` 其实内置了这个：
> `PositionSmoothingEnabled` + `PositionSmoothingSpeed`。
> 本站刻意自己实现，是为了让这行数学显式地摆在你面前 ——
> 知道它在做什么，调参数时才不是瞎试。

## 三、核心概念二：创伤式屏幕震动

```csharp
public void Shake(float trauma)      // 加一点"创伤"，0~1，会叠加但不超过 1
{
    Trauma = Mathf.Min(1f, Trauma + trauma);
}

// 每帧：
Trauma = Mathf.Max(0f, Trauma - Decay * delta);
var amount = Trauma * Trauma;        // ← 关键：平方
offset = random_unit_vector * amount * MaxOffset;
```

**为什么用"创伤值"而不是"震动时长"**：

1. **连续受击会自然叠加**。如果用"震动 0.2 秒"这种写法，
   第二下命中会把第一下**打断**（重置计时器），快节奏下震动会显得"粘不住"。
   创伤值则是累加，连着打三下就是三倍冲击，然后一起衰减。
2. **平方让衰减曲线更自然**。线性衰减看起来像机器在匀速晃；
   平方之后是"前段猛、后段干脆"，符合直觉。
   这个技巧出自 Squirrel Eiserloh 的 *Juicing Your Cameras* 演讲，几乎是行业标准。
3. **强度可换算**。本站的撞击柱把玩家速度换算成创伤值（`speed / 260`），
   于是"轻轻蹭一下"和"全速撞上去"的震动幅度明显不同。
   **固定值的震动会让所有撞击看起来一样重。**

还有一个容易忽略的细节：**抖动不要参与平滑**。
`GlobalPosition = baseline + shakeOffset` —— 基线平滑，抖动直接叠。
如果连抖动一起平滑，它会被"追上去"的过程吃掉，看起来软绵绵的毫无冲击力。

## 四、核心概念三：顿帧

```csharp
public void Hitstop(float realSeconds, float timeScale = 0.05f)
{
    Engine.TimeScale = timeScale;
    _hitstopEndUsec = Time.GetTicksUsec() + (ulong)(realSeconds * 1_000_000.0);
}
```

**顿帧就是临时把时间调慢**，不改变任何游戏逻辑，只改变"时间流逝的速度"。
0.06 秒 / 0.05 倍是常用的量级 —— 再长就会显得卡顿而不是有力量。

三个必须注意的地方：

1. **必须用真实时间判断何时恢复。** 如果用 `delta` 累加计时，
   而 `delta` 本身已经被 `TimeScale` 缩放了，那么"0.06 秒"会变成"1.2 秒"。
   `Time.GetTicksUsec()` 不受 `TimeScale` 影响，本站用的就是它。
2. **负责恢复的那个节点必须一直运行。**
   本站把 `ScreenFx` 的 `ProcessMode` 设成了 `Always`，
   否则它在极低时间缩放下可能被跳过，就没人负责恢复了。
3. **★ 离开场景前一定要复位。**
   `Engine.TimeScale` 是**全局**的。带着 0.05 的时间缩放切换场景，
   新场景会以二十分之一的速度运行 —— **看起来就像游戏卡死了，而且没有任何报错**。
   本站的兜底是 `StationBase._ExitTree()` 里调用 `ScreenFx.Instance.CancelAll()`。
   这种"全局状态忘了复位"是最难查的一类 bug，见到就要立刻加兜底。

## 五、核心概念四：前瞻与边界

**前瞻（look ahead）**：相机朝玩家关注的方向偏移一点。
不前瞻的话，你永远只能看到角色前方半个屏幕，反应时间被砍掉一半。
本站用**鼠标方向**做前瞻（`GetGlobalMousePosition()`），
实际项目里常用"角色朝向"或"移动方向"。

注意前瞻本身也要平滑，而且**要比相机本体更慢**（本站 `LookAheadSharpness = 4`，
相机 `FollowSharpness = 9`）—— 否则鼠标一动画面就跟着甩，非常晕。

**边界（limits）**：相机不该拍到关卡外面的黑区。
`LimitLeft/Top/Right/Bottom` 一设就生效，但有个副作用要提前想清楚：

> **limit 生效时，角色会偏离屏幕中心。**

平时角色永远在正中，一旦走到地图边缘，相机被卡住不动，
角色就会往屏幕边上滑 —— 玩家会明显感觉"相机卡住了"。
很多商业游戏会额外做一个"边界内软化"（相机贴边时略微放宽一点，
让角色不至于贴到屏幕最边上）来缓解这个突兀感。

本站把这条做成了可视化的：**关掉开关 `5`，相机就会拍到关卡外的深色区域**，
你会立刻理解 `limit` 到底在防什么。

## 七、五条练习任务的提示

### ① 实现屏幕震动：撞墙时按力度抖动并衰减
**难度**：★★
已经能用了。要做的练习：

1. 把 `ScreenFx.TraumaDecay` 从 `2.4` 改成 `0.8`，撞一次柱子。
   （提示：会变成"摇一摇"而不是"撞一下"。**衰减速度决定了震动的"性格"**。）
2. 把 `MaxShakeOffset` 改成 `90`，再撞一次。
   （提示：会晕。真实项目里超过 40 像素的屏幕震动就已经很难受了。）
3. **真正的练习**：把平方去掉（`var amount = Trauma;`），再撞一次。
   对比一下线性衰减和平方衰减，说出区别。
4. 进阶：现在的抖动是**每帧随机**的，所以在 30fps 下会明显更"抖"。
   改成用 `FastNoiseLite` 或正弦叠加，让它变成"摇晃"而不是"抖动"，
   并回答：为什么这样改之后帧率就不影响了？

### ② 实现顿帧
**难度**：★★
现有实现只顿帧，没有做"顿帧期间禁止输入"。
想一想：如果顿帧期间玩家还能移动，那个"时间凝固"的感觉还在吗？

练习：
1. 把 `Hitstop(0.06f)` 改成 `Hitstop(0.5f)`，打一下假人。
   （提示：这不是打击感，这是卡顿。）
2. 在 `ScreenFx.Hitstop` 里加一个事件 `HitstopStarted`，
   让站台在顿帧期间把玩家的 `MaxSpeed` 临时设成 0。
   （这是很多动作游戏的做法：**顿帧期间冻结输入，只放行特效**。）
3. 想一想：为什么顿帧要放在**命中判定之后**，而不是之前？

### ③ 给相机加 limits
**难度**：★
本站已经做了。练习：

1. 按 `5` 关掉边界，走到地图外面看看。
2. 把 `Arena` 改成比屏幕还小（比如 `Rect2(0, 0, 900, 500)`），
   观察相机"完全不能动"的现象。
   （提示：当关卡比视口还小时，`limit` 会让相机卡死在中间 ——
   这时候正确的做法是**让相机居中并禁用跟随**，而不是继续套 limit。）
3. 实现"边界软化"：相机贴边时，让角色最多只偏离中心 30% 屏宽。

### ④ 加「前瞻」：相机朝鼠标方向最多偏移 40 像素
**难度**：★★
现有实现已经有了。练习：

1. 把 `LookAheadMax` 改成 `(200, 150)`，走一走。
   （提示：会晕。**前瞻的幅度和相机移动量是两回事**，
   前瞻太大就等于"画面在跟着鼠标甩"。）
2. 加一个"速度前瞻"：不仅看鼠标，还要朝**移动方向**偏移，
   移动越快偏得越多（像赛车游戏那样）。
3. 想一想：前瞻应该用鼠标方向、角色朝向、还是移动方向？
   这三者在什么类型的游戏里更合适？

### ⑤ 对比：位置直接跟随 vs 平滑插值
**难度**：★★
按 `3` 就能切换。**但真正的对比要做这件事**：

1. 先按 `3` 关掉平滑，绕地图走一圈（本站会统计你走了多少像素）。
2. 再按 `3` 打开平滑，走同样的一圈。
3. 回答：关掉平滑时，为什么"画面很晃"？
   （提示：玩家的 `Velocity` 是**每帧突变**的 —— 加速、刹车、转向都是瞬间的。
   直接跟随等于把速度的突变原封不动传到画面上。
   **平滑的本质是滤掉高频抖动，代价是引入延迟。**）
4. 把 `FollowSharpness` 从 `9` 调到 `2`，感受"延迟"的那一端。
   **所有平滑都是在"抖"和"拖"之间找一个点**，没有免费的午餐。

## 八、常见坑速查

| 现象 | 原因 |
|---|---|
| 换场景后整个游戏变成慢动作 | 顿帧没复位 `Engine.TimeScale`。必须在退场时兜底 |
| 顿帧持续了 1 秒而不是 0.06 秒 | 用了被缩放的 `delta` 计时。要用 `Time.GetTicksUsec()` |
| 高帧率下相机比低帧率跟得紧 | 用了 `Lerp(a, b, 常数)`。要用 `1 - exp(-k·dt)` |
| 屏幕震动软绵绵的没冲击力 | 抖动参与了平滑。抖动应该直接叠在平滑结果上 |
| 连续受击时震动"断了" | 用了"震动时长"而不是"创伤累加" |
| 相机拍到了地图外的黑边 | 没设 `LimitLeft/Top/Right/Bottom`，或者设的范围比视口还小 |
| 角色走到地图边缘就贴到屏幕边上 | 这是 limit 的正常副作用。需要额外做"边界软化" |
| 相机跟着鼠标乱甩 | 前瞻的平滑系数比相机本体还快。前瞻要**更慢** |

## 九、通关后做什么

1. **关掉全部五个开关，再通关一次。** 你会发现这一站变得极其难受 ——
   那个"难受"的量，就是这五个效果的价值。
2. 想一想：**为什么本站的撞击柱要用一个"略大一圈的 Area2D"来检测撞击？**
   （提示：如果用碰撞本身触发，读到的 `Velocity` 已经被物理求解归零了，
   震动强度就永远算不对。**"先感觉到、再挡住"是撞击反馈的标准做法。**）
3. 去 `common/fx/ScreenFx.cs` 看 `CancelAll()` 被谁调用。
   然后想想：还有哪些"全局状态"需要同样的兜底？
   （提示：`Engine.TimeScale`、`Input` 的按键状态、`AudioServer` 的总线静音、
   `Input.MouseMode` —— 这些都是全局的，忘了复位就会出现"退出某个界面后整个游戏不对劲"。）
4. 打开 `F3` 性能面板，撞一次柱子 —— 观察帧时间有没有变化。
   （屏幕震动本身开销极小，但你会在 S14 学到：**每帧新开 Tween 和随机数是有成本的**，
   高频特效要用对象池。）
