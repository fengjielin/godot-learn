# S10 · 背包与物品

> **练什么**：数据与视图分离 · 拖拽 · 堆叠 · 装备
> **一句话**：背包的难点**从来不是 UI**，而是「数据模型」和「它怎么显示」必须分开。
> **难度**：★★★★☆（UI 部分很繁琐，但真正的难点是一个架构决定）

---

## 一、先玩一遍

| 操作 | 作用 |
|---|---|
| **鼠标左键**点格子 | 拿起 / 放下（放下就是**交换**） |
| **鼠标右键**点格子 | 使用 / 装备 |
| 键盘 `1`~`5` | 在脚下生成 草药 / 矿石 / 小药水 / 大药水 / 疾行靴 |
| 左键点装备槽 | 把拿着的装备放进去 |

### 实测状态

```
【数据模型】[potion:3][herb:5][herb:1][ore:4][big_potion:1][boots:1]
已用 6/12 格　物品种类 5
```

注意 **`herb:5` 和 `herb:1` 是两格** —— 初始 3 个加上捡到的 3 个一共 6 个，
在「最多叠 5 个」的规则下**溢出到了第二格**。这就是任务 ①。

## 二、核心概念一：数据模型里不该有一行 UI 代码

`common/items/Inventory.cs` **不知道有没有格子、格子长什么样、用图标还是文字**。
它只回答四个问题：

```csharp
public ItemStack? Get(int index);              // 第 i 格是什么
public int TryAdd(string itemId, int count);   // 能不能放进去（返回没放下的数量）
public void Swap(int a, int b);                // 交换两格
public ItemDef? ConsumeOne(int index);         // 用掉一个
```

> **拖拽只是 `Swap` 的一个调用者。** 如果你把拖拽逻辑写进 UI，
> 那么"用键盘移动物品""自动整理背包""从商店直接购买"都要重写一遍。

### 三个视图，一份数据

屏幕上**同时有三处在显示同一份数据**：

| 视图 | 位置 |
|---|---|
| A：12 个格子 | 屏幕中左 |
| B：快捷栏（12 个小方块） | 屏幕左下 |
| C：面板里的「原始数据模型」 | 文字 dump |

**改一格，三处一起变。** 这就是"数据与视图分离"最直观的证据 ——
如果数据是节点，你不可能用三个视图显示它而不用手动同步。

## 三、核心概念二：视图怎么知道要刷新

```csharp
public event Action? Changed;   // 数据变了

// 数据模型里每次改动都通知：
if (remaining != count) Changed?.Invoke();

// 视图订阅它：
_inventory.Changed += RefreshViews;
```

**数据变了通知视图，而不是视图每帧去问数据。**

两种做法各有代价：

| | 事件通知 | 每帧轮询 |
|---|---|---|
| 开销 | 只在变化时 | 每帧都花（哪怕什么都没变） |
| 漏更新 | 忘了 `Invoke()` 就漏 | 不会漏 |
| 调试 | 要追"谁触发了它" | 一眼看出在哪刷新 |

> 本站的 `RefreshViews()` **整体重画所有格子**，不做"只更新变了的那一格"。
> 因为**在能跑之前不需要优化**，而且差异更新是 bug 的温床 ——
> 漏更新某一格 = 画面和数据不一致，而且只在特定操作序列下出现。
>
> **20 个格子的整体重画，一帧不到 0.01ms。这个优化根本不值得做。**

## 四、核心概念三：堆叠规则（任务 ①）

```csharp
public int TryAdd(string itemId, int count)
{
    // ① 先填已有的、没满的同类堆
    // ② 塞不下的部分再开新格子
    // ③ 格子用完了，剩下的加不进去 —— 返回没加进去的数量
}
```

**这里的每一个决定都值得想一遍：**

1. **先填旧堆还是先开新格？** 先填旧堆（本站做法）符合直觉。
   先开新格会让背包很快被半满的堆占满。
2. **格子用完了怎么办？** `TryAdd` **返回没放下的数量**，由调用方决定。
   - 数据模型**不做玩法决定**：是丢地上、是提示"背包已满"、还是自动卖掉 ——
     这是玩法层的选择，不该写死在数据结构里。
3. **堆叠上限该按物品还是按格？** 本站按物品（`ItemDef.MaxStack`），
   所以药水叠 3 个、材料叠 5 个、装备不叠。

## 五、核心概念四：为什么不该把「图标节点」当作数据（任务 ⑤）

如果你把 `TextureRect` / `Label` 存进背包格子，会发生什么：

| 问题 | 后果 |
|---|---|
| **存档没法存** | 节点不能被 JSON 序列化（S11 教的：存数据，不存对象） |
| **排序 / 搜索没法做** | 你得去问每个节点"你是什么物品" —— 而节点不回答这种问题 |
| **换显示方式要重写全部逻辑** | 想加个列表视图，就得改背包本身 |
| **数据被节点的生命周期绑住** | 界面一刷新（比如切场景），数据可能就没了 |
| **做不了多视图** | 本站的三个视图会变成三份数据，然后你花在"同步"上的时间比写功能还多 |
| **逻辑没法单测** | 想测"堆叠溢出"就得先建一个场景、造一堆节点 |

> **判据一句话：这东西在"没有屏幕"的情况下还有意义吗？**
> "草药 ×3"有意义；"那个绿色的方块节点"没有。

## 六、代码地图

| 文件 | 负责什么 |
|---|---|
| `common/items/Items.cs` | `ItemDef`（定义）/ `ItemStack`（一格里的东西）/ `ItemDatabase` |
| `common/items/Inventory.cs` | ★ **纯数据模型**：堆叠 / 交换 / 消耗 / 变更事件 |
| `src/stations/s10_inventory/S10Inventory.cs` | 站台：三个视图 + 鼠标交互 + 装备与使用 |

**`ItemStack` 也只是一个数据对象** —— 没有节点引用、没有绘制代码，
只有一个 `ItemId` 和一个 `Count`。所以它能被 `Clone()`、能被塞进列表、能直接序列化。

## 七、五条练习任务的提示

### ① 实现堆叠：同种物品最多叠 5 个，超出占新格子
**难度**：★★★ 已经做了（实测 `herb:5` + `herb:1`）。

练习：
1. 把 `ItemDatabase` 里草药的 `MaxStack` 改成 `1`，然后捡 6 个草药 ——
   **它们会占 6 格**。背包的"容量感"立刻完全不同。
2. 加"**自动整理**"：把所有物品按 id 排序、重新堆叠。
   **回答**：它应该改数据模型，还是只改视图？
   （提示：改数据模型 —— 因为"整理后的顺序"是要存进存档的。
   如果只改视图，读档回来又乱了。）
3. **挑战**：加"**部分堆叠**" —— 比如从商店买 10 个草药，
   而背包只剩 2 格 × 5 = 10 的空间。返回"成交了几个"，
   并让商店按实际成交数扣钱。**回答**：这个逻辑该写在背包里还是商店里？**

### ② 实现拖拽交换两个格子
**难度**：★★★ 已经做了（"拿起 / 放下"就是一种拖拽，而且**更适合键盘和手柄**）。

练习：
1. 现在是"点一下拿起、再点一下放下"。改成**真正的鼠标拖拽**
   （`_GetDragData` / `_CanDropData` / `_DropData`）。
   **回答**：真拖拽比"点两下"好在哪？坏在哪？
   （提示：好在直观；坏在**手柄和键盘用不了**，而且长距离拖动很累。
   很多主机游戏的背包就是"点两下"的。）
2. 加"**Shift + 点击 = 快速移动**"（背包 ↔ 装备槽）。
   **这是所有 ARPG 的标配操作**，比拖拽快得多。
3. **挑战**：加"**拖到空格子 = 移动，拖到同类物品 = 合并，拖到异类 = 交换**"。
   注意这三种情况的判定顺序 —— **合并必须优先于交换**，
   否则同类物品永远叠不起来。

### ③ 加装备槽，装备后移动速度变化
**难度**：★★★ 已经做了（疾行靴 +45%，重甲 −20%）。

练习：
1. 按 `5` 生成疾行靴 → 左键拿起 → 左键点靴子槽。
   面板右下角的"移动速度"会变成 `×1.45`。
2. **回答**：装备的属性加成应该**累加**还是**累乘**？
   （提示：+45% 和 −20% 累加 = +25%；累乘 = 1.45 × 0.8 = +16%。
   **累乘更"公平"但更难平衡，累加更容易出现负值爆炸。**）
3. **挑战**：加"**套装效果**"（穿齐两件 +10%）。
   回答：这个判定该放在哪？（提示：**不该放在物品里，也不该放在装备槽里，
   而是放在"重新计算角色属性"的那个地方** ——
   因为它是"整体"的属性，不是任何单件物品的属性。）

### ④ 加右键使用物品：药水回血
**难度**：★★ 已经做了。

练习：
1. 按 `3` 生成小药水，捡起来，右键点它 —— 生命会回满。
2. **回答**：为什么 `UseSlot()` 里要 `switch (def.Kind)`，
   而不是给每个 `ItemDef` 加一个 `Use()` 委托？
   （提示：两者都行。委托更灵活，但也**让"某个物品的行为"散落在注册代码里**。
   本站选择了 `switch`，因为物品只有三种，**能一眼看全所有分支**。
   **等种类多了、或者要让策划配置行为时，再改成数据驱动。**）
3. **挑战**：加"**使用冷却**"和"**使用中被攻击打断**"。
   前者在 S16 状态效果里有现成做法，后者需要和 S07 的伤害管线接上。
   **这一题做完，你就把三个系统串起来了。**

### ⑤ 思考：为什么不该把「图标节点」本身当作数据？
**难度**：★★★
用第五节那张表回答：

1. **"当前选中的格子下标"** 该存在数据模型里还是视图里？
   （提示：**视图里**。它是"你正在看的东西"的状态，不是物品的状态。
   存进数据模型的话，存档里就会出现"上次选中了第 3 格"这种没意义的数据。）
2. **"物品的耐久度"** 呢？（提示：**数据模型**。它会变，而且要存进存档。）
3. **"格子是第几行第几列"** 呢？（提示：**视图**。换成列表视图之后就没有行列了。）
4. **"物品的稀有度"** 呢？（提示：**ItemDef**。它不变，而且是物品的固有属性。）
5. 最后一题：**本站的 `_heldSlot`（手上拿着哪一格）存在站台里，而不是 `Inventory` 里。**
   为什么？（提示：因为它是**交互过程的状态**，不是背包的状态。
   换个操作方式（比如真拖拽）就没有"手上"这个概念了。）

## 八、常见坑速查

| 现象 | 原因 |
|---|---|
| 存档存不了背包 | 把节点当数据存了。**数据模型里不能有节点** |
| 两个视图显示的内容不一致 | 各自维护了一份数据。**必须只有一份，视图只读它** |
| 画面和数据不一致，但只在某些操作后 | 手工做"差异更新"漏了某一格。**先整体重画，需要时再优化** |
| 同类物品永远叠不起来 | 拖拽的判定顺序错了。**合并必须优先于交换** |
| 背包满了之后物品凭空消失 | `TryAdd` 返回了剩余量，但调用方没处理。**永远检查返回值** |
| 掉在地上的物品捡不起来 | 生成点和拾取半径不匹配（**本工程踩过：掉在 70px 处，半径只有 42**） |
| `GuiInput` 收不到鼠标事件 | 控件的 `MouseFilter` 是 `Ignore`。**要收事件就设成 `Stop`** |
| 换了一种视图就要重写逻辑 | 逻辑写在视图里了。**回第二节重看一遍** |

## 九、通关后做什么

1. **把 `Inventory` 复制出来，删掉所有和 UI 有关的东西**（本站的它本来就没有）。
   然后**不看引擎、只用 `dotnet test` 给它写三个测试**：
   堆叠溢出、背包满、交换。
   **你会发现这是本工程里最容易测的一个类** —— 因为它不认识 Godot。
2. 想清楚：**本站的 `Inventory` 为什么没有做成 Autoload？**
   （提示：因为只有一个地方用它。**等第二个使用者出现再提升，不要提前全局化。**
   S11 的 `SaveSlots` 也是同样的处理。）
3. 回到 S11 存档站，把 `Inventory.Snapshot()` 存进槽位，
   读档时还原。**回答**：`ItemStack` 需要加什么才能被 JSON 序列化？
   （提示：它已经可以了 —— 两个公开属性都是简单类型。
   **这就是"数据模型干净"的回报：存档不用改一行代码。**）
4. 去 `docs/00-学习路线图.md` 看一眼自检清单里 S10 那两条，确认你能答上来。
