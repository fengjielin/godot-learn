# S15 · 程序化生成

> **练什么**：种子随机 · 噪声 · 房间生成 · **连通性验证** · 生成耗时分解
> **一句话**：同一套算法 + 同一个种子 = 同一个世界。**可复现是关键。**
> **难度**：★★★★☆（写出一个算法不难，写出一个**每张图都能玩**的算法很难）

## 二、核心概念一：可复现（本站的灵魂）

> **种子是程序化生成的 bug 报告格式。**

玩家报"我这局出生在墙里了"，你没法复现就完全无从下手。
有了种子，他只要把种子告诉你，你就能看到**一模一样**的那张地图。

### ★ 最常见的一种不可复现：全局随机

```csharp
// ❌ 用地全局随机函数
if (GD.Randf() < 0.4f) grid[x, y] = true;

// ✅ 用自己持有的、只由种子决定的发生器
var rng = new RandomNumberGenerator { Seed = (ulong)seed };
if (rng.Randf() < 0.4f) grid[x, y] = true;
```

为什么全局随机会毁掉可复现？**因为它的状态会被游戏里任何一处随机调用污染。**

你在生成前多捡一个金币、多播一次随机音高的音效、多摇一次暴击 ——
地图就变了。而且**只在某些流程下才变**，于是它表现为"偶尔复现不了"。

**本站的 `5` 键就是用来验证这一点的**：它连调 1000 次 `GD.Randi()` 把全局随机搅乱，
然后你按 `3` —— 指纹依然一致，**因为生成器根本不碰全局随机**。

> 想验证自己的项目有没有这个毛病，就用同样的方法：
> **在生成前后故意调用几百次全局随机，看结果变不变。**

### 指纹

```csharp
private string ComputeFingerprint()
{
    var hash = 17;
    for (var x = 0; x < Width; x++)
    for (var y = 0; y < Height; y++)
        hash = unchecked(hash * 31 + (Grid[x, y] ? 1 : 0));
    return hash.ToString("X8");
}
```

把整张地图压成一个 8 位十六进制串。**两次生成指纹相同 = 地图完全相同。**
这比"看起来差不多"可靠得多，而且**可以直接打进日志和 bug 报告里**。

## 三、核心概念二：三种算法各自的性格

| 算法 | 原理 | 优点 | 致命缺点 |
|---|---|---|---|
| **随机撒点** | 每格按概率变墙 | 两行代码 | **几乎一定不连通** |
| **噪声洞穴** | `FastNoiseLite` 取阈值 | 自然的洞穴形状，参数连续可调 | 连通性看运气 |
| **BSP 房间** | 递归切分 → 挖房间 → 连走廊 | **结构清晰、天然连通、可控** | 长得"规整"，不够有机 |

> **随机撒点这一个选项是故意留着不修好的。**
> 它是用来演示"为什么必须验证连通性"的对照组 ——
> 打开它，你会看到连通区有几十个，地图根本没法玩。

### FastNoiseLite 的关键参数

- `Frequency`（频率）：越大越碎。0.085 对本关的格子尺寸刚好。
- `FractalOctaves`（分形层数）：把不同频率的噪声叠加。层数越多细节越丰富，也越慢。
- **噪声是连续的** —— 相邻格子的值接近，所以会形成"片"而不是"噪点"。
  **这正是它比随机撒点更适合做地形的根本原因。**

## 四、核心概念三：连通性验证（任务 ③）

```csharp
// 洪水填充：从每个未访问的可走格子出发，标出相连的一整片
while (queue.Count > 0) { ... }   // 四个方向扩散
RegionCount++;                     // 数出一共有几片
```

**`RegionCount == 1` 才说明整张地图是通的。**

> ★ 为什么必须验证：随机撒点的地图**大概率是不连通的**。
> 如果玩家出生在 A 区、出口在 B 区，游戏直接卡死 ——
> 而且这种 bug **只在某些种子下出现**，靠手动试玩几乎不可能发现。
>
> **程序化生成必须自带验证，因为「你没法把每一张地图都玩一遍」。**

### 发现不连通之后怎么办

本站提供了"**只保留最大连通区**"（把其他区域的格子填成墙）。这是最省事的做法，
代价是丢掉一部分空间。更讲究的做法是把各区域**用走廊连起来** ——
BSP 算法就是这么干的（它在生成阶段就把连通性做进了结构里）。

**两种思路的取舍**：
- **事后修复**（flood fill + 填补）：能用在任何算法上，但浪费空间
- **结构性保证**（BSP / 走廊连接）：不浪费，但只对特定算法有效

> **能靠结构保证的事情，不要靠事后检查。** 检查是兜底，不是方案。

## 五、核心概念四：耗时的三段（任务 ⑤）

生成一屏地图的时间花在三个地方，**它们是完全不同的问题，优化手段也完全不同**：

| 阶段 | 本站实测 | 优化手段 |
|---|---|---|
| ① 算法（生成网格 + flood fill） | **0.11ms** | 换算法、减少遍历、把 flood fill 放到后台线程 |
| ② 建节点（800 个 `Polygon2D` + 碰撞 + 导航） | **8+ms** | **别一格格建节点** |
| ③ 导航网格烘焙 | （含在 ② 里） | 增量更新，或者只烘焙玩家附近的区域 |

**本站的瓶颈明明白白在 ②**，而且 ① 已经被优化到几乎免费。

> **"怎么把 100ms 降到 10ms"的答案，取决于这 100ms 花在哪。**
> 大多数人的直觉是去优化算法 —— 而真正的答案往往是"别创建那么多节点"。

### ② 的三种解法

1. **`TileMapLayer`** —— Godot 为瓦片地图准备的节点。它把成百上千个格子
   合并成极少量的绘制调用。**代价**：需要准备一个 TileSet（一张纹理图集）。
2. **`MultiMeshInstance2D`** —— 用同一份网格数据画 N 个实例，
   位置由代码填进一个 transform 数组。**代价**：里面的东西不是节点，
   没有 `_Process`、没有碰撞、没有信号。
3. **只生成可见区域** —— 屏幕外的格子先不建节点。
   **代价**：需要管理"玩家移动时补建/回收"的逻辑。

**三者的共同点：都是在"用更少的节点表达更多的东西"。**
这也是 S14 那句话的延续 —— **先测量，再优化。**

## 六、核心概念五：一份数据，三种用途（S08 的纪律）

```csharp
// 墙的矩形只生成一次
foreach (var wall in _generator.WallRects(Origin))
    LevelKit.AddWallShape(_wallBody, ...);          // ① 撞得到

_navRegion.NavigationPolygon =
    NavMeshBuilder.BuildFromWalls(area, _generator.WallRects(Origin));   // ② 走得到
```

**画面、碰撞、导航全部来自 `_generator.Grid` 这一份数据。**
如果它们各用一份，你迟早会遇到"敌人撞在看不见的墙上"，
而且两边单独看都是对的 —— **极难调试。**

**为什么 `DungeonGenerator` 一行 Godot 节点代码都没有？**
两个原因：① 只有这样才能**单独测量算法耗时**（任务 ⑤ 的前提）；
② 纯算法可以脱离引擎单测 —— **把"算什么"和"画什么"分开，是让生成可测试的前提。**

## 八、五条练习任务的提示

### ① 支持输入种子，让同一颗种子每次生成完全一样的地图
**难度**：★★ 已经做了。练习：

1. 按 `5` 污染全局随机，再按 `3` —— 指纹不变。**然后**把 `DungeonGenerator`
   里的 `rng.Randf()` 改成 `GD.Randf()`（只改算法一里的那一处），
   再重复同样操作 —— **地图变了**。**这就是不可复现的样子。**
2. 给面板加一个"手动输入种子"的输入框（提示：`LineEdit` 的 `TextSubmitted` 信号）。
3. **回答**：种子应该存在存档里吗？（提示：**该存**。玩家退出再进来，
   应该回到同一张地图 —— 否则他建的基地就没了。）

### ② 切换三种算法：随机撒点 / FastNoiseLite 洞穴 / BSP 房间
**难度**：★★★★ 已经做了。练习：

1. 给噪声洞穴加一个"**平滑**"后处理：把周围墙数 ≥5 的格子变成墙、
   ≤3 的变成空地，重复 3~4 次。这是经典的 cellular automata 洞穴算法。
   **回答**：它改善了连通性吗？为什么？
2. 给 BSP 加一个"**房间最小尺寸随深度变化**"的规则，让大房间里套小房间。
3. **挑战**：加第四种算法 —— **迷宫生成**（递归回溯 / Prim）。
   然后回答：**迷宫和洞穴在"可玩性"上有什么本质区别？**
   （提示：迷宫的"可走格子比例"极低，玩家会走得很憋屈。
   所以很多游戏会用"迷宫 + 额外打通一些墙"来兼顾。）

### ③ 保证所有房间连通（用 flood fill 验证）
**难度**：★★★ 已经做了。练习：

1. 切到"随机撒点"、关掉连通性修复 —— 看连通区有几个。
   然后按 `3` 多试几次，**记录连通区数量的分布**。
   **回答**：它有没有可能"碰巧全连通"？概率大概是多少？
2. 把"保留最大连通区"换成"**把各区域用走廊连起来**"。
   后者更复杂但保留空间。**实现它，然后比较两者的可走格子数。**
3. **挑战**：加一个"**可达性**"检查 —— 不只检查连通，
   还检查"出生点到出口的最短路径长度"是否在合理范围内。
   **回答**：为什么"连通"还不够？**（提示：连通但要走 200 步的地图，玩家体验一样糟。）**

### ④ 用 TileMapLayer 把生成结果画出来
**难度**：★★★★（这一条要你动手）
本站用的是**一格格建 `Polygon2D`** —— 800 个节点，建了 8ms。
这正是任务 ⑤ 说的瓶颈。

练习：
1. 建一个最小 TileSet（一张 2×2 像素的小图都行，两格分别是墙和地板），
   用 `TileMapLayer.SetCell()` 把网格铺上去。
2. **测一下建节点耗时变成了多少。**（预期：从 8ms 降到 1ms 以内。）
3. **回答**：TileMapLayer 为什么快这么多？
   （提示：它的绘制调用数几乎和地图大小无关。**这就是 S14 讲的"绘制调用"的价值。**）
4. 对比 `MultiMeshInstance2D` 的做法，**回答：什么情况下你会选 MultiMesh 而不是 TileMapLayer？**
   （提示：当"每格看起来都不一样"、用不上图集的时候。）

### ⑤ 加生成耗时统计，思考怎么把 100ms 降到 10ms
**难度**：★★★ 已经做了（而且发现瓶颈根本不在算法）。
练习：

1. 把 `RebuildVisuals` 里的 `Polygon2D` 换成**只创建一次、之后只改颜色**
   （不 `QueueFree` 再重建）。测一下耗时变化。
2. 把 flood fill 放到**后台线程**（`System.Threading.Tasks.Task`）跑。
   **回答**：这样改有意义吗？（提示：看它占 0.11ms 里的多少。）
3. **最重要的一问**：如果你的生成总耗时是 100ms，而其中 95ms 是建节点 ——
   **你应该把精力花在哪？** 如果花在优化 flood fill 上，能省多少？
4. 想清楚"**异步生成**"这件事：如果生成要 200ms，能不能让玩家先看到加载界面，
   在后台生成完再进游戏？（提示：这就是"用时间换流畅"，而不是"用算法换时间"。）

## 九、常见坑速查

| 现象 | 原因 |
|---|---|
| 同种子生成出不同的地图 | 用了全局随机（`GD.Randf()`）。**必须用自己持有的 RNG** |
| 偶尔才复现不了 | 全局随机被别处污染了。**用 1000 次 `GD.Randi()` 的方法验证** |
| 玩家出生在墙里 | 出生点没有校验。**必须从 `Grid` 里挑一个可走格子** |
| 有些地方永远走不到 | 地图不连通，而且没做验证 |
| 地图看起来对，但敌人撞墙 | 碰撞体和导航网格用的是两份数据。**必须同源** |
| 生成很慢，但算法本身很快 | 瓶颈在建节点。**先分段测量，别猜** |
| 换了算法之后某个种子崩了 | 不同算法对边界的假设不同（比如 BSP 假设区域 ≥ 某尺寸） |
| `FastNoiseLite` 生成的地图全是墙/全是地 | `Frequency` 或阈值不对。**先输出一格直方图看看分布** |

## 十、通关后做什么

1. **把 `5` 键的效果真正用起来**：打开你自己项目里的生成代码，
   把所有 `GD.Randf()`/`randi()` 找出来。**只要有一处，可复现就是假的。**
2. 想清楚：**种子该存在哪？**（提示：S11 存档。而且要注意 ——
   **"地图种子"和"这一局的随机种子"是两个东西**：
   前者决定地形，后者决定掉落和暴击。混在一起的话，
   玩家多打一只怪，地形就变了。）
3. 做一个"**生成质量评分**"：可走格子占比、连通区数、房间数量、
   出生点到最远点的距离。然后**随机跑 1000 个种子**，看有多少张地图评分不合格。
   **这一步做完，你才算真正知道自己的生成器靠不靠谱。**
4. **这一站之后只剩两站了。** 回到 `docs/00-学习路线图.md`，
   你会发现"程序化生成"是自检清单里少见的、**没有标准答案**的一条 ——
   因为它的好坏取决于你想要什么样的游戏。
   **这正是从"学引擎"到"做设计"的分界线。**
