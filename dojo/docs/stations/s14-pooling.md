# S14 · 对象池与性能

> **练什么**：对象池 · 性能测量 · 节点数 · 绘制调用 · 什么时候**不**该池化
> **一句话**：**先测量，再优化。** 没有数字就改代码，99% 是在浪费时间。
> **难度**：★★★☆☆（写池不难，难的是"判断这里到底值不值得池化"）

## 二、实测数据（本站自己跑出来的）

先按 `4` 预热，然后 `1` / `2` 各跑几次：

```
【对比】           生成耗时    之后 1.5s 平均帧时间    节点增量
朴素 Instantiate    90.4ms         16.67ms            3600
对象池复用          14.1ms         16.67ms               0

→ 生成阶段省下 76.3ms（朴素 90.4ms → 池化 14.1ms）
→ 之后每帧省下 0.00ms（朴素 16.67ms → 池化 16.67ms）
→ 差距很小，这个场景池化可有可无
```

**最后那句是程序自己算出来的，不是写死的。** 它想让你看到两件事：

1. **池化在"生成"这一步赢了 6.4 倍**（90.4ms → 14.1ms），而且**节点增量为 0**
   —— 朴素模式跑了三轮，创建销毁了 3600 个节点；池化预热之后再没 new 过任何东西。
2. **在"稳态帧时间"这一步，赢面小到测不出来。**

> **池化省下的不是"对象"，而是「创建和销毁」这两件事。**
> 如果对象寿命很短、每秒创建销毁几百次（子弹、粒子、飘字），它很值。
> 如果屏幕上同时只有十几颗子弹、寿命好几秒，池化带来的收益可能还不如它增加的复杂度。

**这就是"先测量，再优化"的意思。**
你可能在优化一个根本不是瓶颈的地方，也可能把一个 0.2ms 的问题优化成 0.1ms
然后觉得自己很厉害。

> ⚠️ **一个测量上的坑**：如果你用 `--write-movie`（本工程做自动化截图时用的）
> 跑这一站，Godot 会把时间步长固定成 60FPS，于是"平均帧时间"永远是 16.67ms ——
> **那一列就失去了意义**。想量真实的帧时间，要正常启动游戏，
> 而且要**关掉垂直同步**（否则帧率会被锁在显示器刷新率上，什么差别都看不出来）。
> 面板里的"生成耗时"和"节点增量"是真数据，不受这个影响。

## 三、核心概念一：池化的两条铁律

```csharp
public void Launch(...)
{
    // ① 所有会残留的状态都在这里重置
    Position = ...; Rotation = 0; Scale = Vector2.One; Modulate = Colors.White;
    _age = 0; _body.Color = ...;
    InUse = true; Visible = true;
}

public void Release()
{
    InUse = false;
    Visible = false;
    if (AutoFree) QueueFree();   // ② 只有"不在池里"的时候才自己销毁
}
```

1. **`Launch()` 必须重置所有字段。** 漏掉任何一个，下一轮复用时它会带着上一次的痕迹出现 ——
   这种 bug 看起来像"随机发生"，其实是漏了一个字段。
2. **池化对象不能自己 `QueueFree`。** 它只能把自己标记为空闲，
   **销毁权必须只有一方持有**。本站用一个 `AutoFree` 开关同时支持两种模式做对比，
   真要混用的时候必须非常小心。

**池应该"按需增长"还是"预先预热"？**
- 按需增长：启动快，但第一次爆发时仍会有 Instantiate 的开销（而且恰好在你最需要性能的时候）
- 预热：把开销挪到加载画面里 —— 但预热太多会浪费内存

本站两种都做了：`4` 预热到 1200，之后 `2` 就不再 new 任何东西（节点增量为 0 就是证据）。

## 四、核心概念二：看性能要看哪几个数

按 `F3` 打开引擎自带面板（`common/debug/DebugHud.cs`），只看四个数就够了：

| 数 | 说明 | 什么时候是问题 |
|---|---|---|
| **帧时间** | 比 FPS 更有意义：7ms 和 14ms 就是 144Hz 与 60Hz 的差别 | 持续超过你的目标帧预算 |
| **节点数** | 暴涨说明在疯狂 Instantiate 而没回收 | 每秒都在涨 = 池化漏了 |
| **绘制调用** | CPU 瓶颈的常见来源 | 成百上千 = 该合批了 |
| **物理时间** | 大量 Area2D / 碰撞体的代价 | 超过帧预算的一半 |

**游戏性能的三层**（优化时按这个顺序查，别跳步）：
1. **算法** —— 有没有 O(n²)？有没有每帧重建数组？（改这里收益最大）
2. **分配** —— 有没有每帧 new？GC 什么时候会触发？（对象池解决的就是这一层）
3. **渲染** —— 绘制调用太多？该合批或降分辨率了。（这条被绝大多数人高估）

## 六、五条练习任务的提示

### ① 实现对象池：预热 200 颗子弹并循环复用
**难度**：★★★
本站预热的是 1200。练习：

1. 把 `BurstCount` 改成 `200`，再对比一次 —— **差距应该会明显缩小**。
   这证明"池化的收益和数量成正比"。
2. 把子弹寿命 `BulletLife` 从 `2.4` 改成 `8`，再对比 ——
   寿命越长，"同时存活"的数量越多，池需要预先准备的实例也越多。
   **池的大小由"峰值同时存活数"决定，不由"总生成次数"决定。**
3. **真正的练习**：把池从"线性扫描找空闲"改成"用栈/队列管理空闲表"。
   现在 `RentFromPool()` 是 `foreach` 线性扫描 —— 池越大越慢。
   用一个 `Stack<PoolBullet>` 存空闲实例，`Rent` 就是 O(1)。
   改完再测一次生成耗时，**你会看到又一个数量级的改善，而且这次是在池这一侧**。

### ② 用 MultiMesh 或 RenderingServer 批量绘制，再对比一次
**难度**：★★★★（这一条需要你自己写）
本站的子弹是 `Area2D` + `Polygon2D` —— **每个子弹一个节点**。
所以"节点增量 3600"这件事在池化模式下虽然解决了，
但"3600 个节点同时存在"的**渲染开销**还在（面板上绘制调用 169）。

练习：用 `MultiMeshInstance2D` 把 1200 颗子弹画成**一批**，
位置由代码每帧填进 `MultiMesh` 的 transform 数组。然后回答：

- 节点数变成了多少？
- 绘制调用变成了多少？
- **代价是什么？**（提示：MultiMesh 里的东西不是节点，
  所以没有 `_PhysicsProcess`、没有碰撞、没有信号。**你换到的是性能，付出的是"可编程性"。**）

### ③ 打开 F3 调试面板，记录三种做法的 FPS 与节点数
**难度**：★
三种做法 = 朴素 / 池化 / MultiMesh。练习：

1. 做一张表，把三次的**节点数、绘制调用、帧时间**填进去。
2. **回答：哪一项是瓶颈？** 不要三样一起改 —— 一次只改一个变量。
3. 想一想：如果你只测 FPS 而不测节点数和绘制调用，
   你能判断出瓶颈在哪吗？（提示：不能。**FPS 是结果，不是原因。**）

### ④ 用 调试器 → 分析器 找到最耗时的函数
**难度**：★★
在 Godot 编辑器里：运行游戏 → 下方**调试器**面板 → **分析器**标签 → 开始录制 →
在游戏里按 `1` 生成 1200 颗 → 停止录制。

你会看到一帧里各个函数占了多少毫秒。练习：

1. 找出 `SpawnNaive` 那一帧里占比最大的是什么。
   （提示：很可能是 `Instantiate` 和 `AddChild`，而不是你的游戏逻辑。）
2. 对比按 `2` 时的分析结果。
3. **回答：为什么"看代码猜瓶颈"几乎总是猜错？**

### ⑤ 思考：对象池什么时候反而更慢？
**难度**：★★★
本站的数据已经给了半个答案（"差距很小，可有可无"）。补全另外几个：

1. **对象很重、寿命很长**：池需要常驻一批内存，占用上升，收益却很小。
2. **池的实现很差**：比如本站现在的线性扫描 —— **池本身成了新的瓶颈**。
   （这就是任务 ① 要你改的原因。）
3. **状态重置写漏了**：你省下了 Instantiate，却引入了"上一轮的痕迹残留"这种诡异 bug。
   **修 bug 的时间可能远超省下的那 76 毫秒。**
4. **对象的创建成本本来就很低**：比如一个纯 C# 的小结构体，
   池化反而要在托管堆和引擎对象之间来回搬。

> **池化是一种用"复杂度和内存"换"分配开销"的交易。**
> 交易划不划算，**只能靠测量**。

## 七、常见坑速查

| 现象 | 原因 |
|---|---|
| 复用的对象带着上次的颜色/大小 | `Launch()` 里漏了重置某个字段 |
| 池化对象被销毁后池还引用着它 | 池化对象自己调了 `QueueFree`。**销毁权只能有一方** |
| 节点数只涨不降 | 忘了 `Release()`，或者 `Release()` 里没 `Visible = false` |
| 池化后反而更卡 | 池的查找是线性扫描，池越大越慢。改用空闲栈/队列 |
| 测不出帧时间差别 | 开了垂直同步（锁 60FPS），或者用 `--write-movie`（固定时间步长） |
| 类名冲突 / 报错行号指向字段 | 两个功能目录下有同名类，且在同一命名空间 |
| 改了代码觉得"应该更快了" | **没有测量。** 这是最贵的一种 bug |
