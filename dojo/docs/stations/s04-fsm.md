# S04 · 状态机

> **练什么**：有限状态机 / 状态转移 / 优先级 / Enter 与 Exit / 可观测性
> **一句话**：把「一堆 if-else 决定角色该干什么」换成**显式的状态 + 一张转移表**。
> **难度**：★★★★☆（写出来不难，难的是"知道它现在在干嘛"——所以本站的重点是那个面板）

---

## 一、先玩一遍

一个守卫，五个状态，一条巡逻路线（场景里那四个绿色菱形）：

```
   Patrol（巡逻）──看到/听到──▶ Alert（警觉）──确认看到──▶ Chase（追击）
        ▲                          │                          │
        │                    警戒时间到                      进入攻击距离
        │                          ▼                          ▼
        └────────────────────── Stun（眩晕）◀──被石头砸中── Attack（攻击）
                                     │
                                苏醒，进入警戒
```

**你能做的三件事**：

| 做什么 | 会发生什么 |
|---|---|
| 走进它的视野（黄色/红色视线代表它看得见你） | 警觉 → 追击 → 攻击 |
| 躲到柱子后面 / 跑远甩掉它 | 追击 → 警觉（丢失目标） |
| 按 `J` 扔石头砸它 | 立刻进入**眩晕** 2 秒 |
| 把石头扔在远处 | 制造动静，它会**跑过去查看** |

**左上角那块面板就是这一站的主角**（见第四节）。

## 二、核心概念一：状态机到底解决了什么

不用状态机的话，AI 会长成这样：

```csharp
// ❌ 一开始能用，两个月后没人敢碰
if (seeTarget) { moveToPlayer(); if (dist < 80) attack(); }
else if (noise) { moveToNoise(); if (arrived) lookAround(); }
if (stunned) { /* 什么都不做 */ }
if (arrived && !seeTarget && alertTimer <= 0) patrol();
...
```

问题不是"不优雅"，而是三个具体的痛：

1. **没法回答"它现在在干嘛"**。上面这段代码运行时处于哪个分支，只能靠读代码推。
2. **优先级靠 if 的书写顺序**。想改"眩晕能不能打断攻击"，你得移动代码位置，
   而且改完很难确认没影响别处。
3. **加状态是 O(n) 的改动**。每加一个状态，所有已有的 if 都要过一遍。

状态机把这三件事都变成显式的：

| | if-else | 状态机 |
|---|---|---|
| 当前状态 | 靠推 | 一个字段，能直接显示出来 |
| 转移条件 | 散落在各分支 | 一张表，能列出来 |
| 优先级 | 书写顺序（隐式） | **注册顺序**（显式，且有文档） |
| 加状态 | 改动所有分支 | 加一个节点 + 几行转移 |

## 三、核心概念二：本站的实现方式

三个文件，都在 `common/state_machine/`：

```csharp
// Transition.cs —— 一条规则：从哪、到哪、什么条件、叫什么名字
new Transition(from: "Chase", to: "Attack", label: "进入攻击距离", () => dist <= 80);

// State.cs —— 一个状态就是一个节点，四个钩子
public virtual void Enter() { }        // 进入时做一次准备
public virtual void Exit() { }         // 离开时收尾
public virtual void Tick(double d) { } // 表现层
public virtual void PhysicsTick(double d) { }  // 位移与判定

// StateMachine.cs —— 驱动 + 一张转移表
Machine.AddState(state);
Machine.AddTransition("Chase", "Attack", "进入攻击距离", () => ...);
Machine.Start("Patrol");
```

**为什么状态是「节点」而不是「类」**：
- 在编辑器的**场景面板里能直接看到有哪几个状态**，不用翻代码找 `enum`；
- **每个状态可以有自己独立的 `[Export]` 参数**，在检查器里单独调，互不干扰。

**为什么转移是「表」而不是 if**：
因为"从 Chase 能去哪些状态"变成了一次**查询**（`Machine.TransitionsFrom("Chase")`），
于是它可以被画到屏幕上。**这正是本站面板能存在的原因。**

## 四、核心概念三：可观测性（本站最重要的部分）

左上角那块面板实时显示四样东西：

```
【状态机】当前 Chase　持续 2.34s　上一次 Alert　累计切换 7 次

从「Chase」出发的转移（自上而下，第一条满足的立刻生效 —— 顺序就是优先级）：
   ▶ 满足　　进入攻击距离　→　Attack
   · 不满足　被石头砸中　→　Stun
   · 不满足　丢失目标超过 1.2 秒　→　Alert

已见过：Patrol✓  Alert✓  Chase✓  Attack✗  Stun✗
最近转移：Alert→Chase  Patrol→Alert
```

**为什么这东西值得占屏幕上一大块地方**：

1. **"当前状态"这一栏，直接消灭了 80% 的 AI 调试时间。**
   玩家说"这个怪卡住了"，你一眼就能看到它是不是卡在 `Alert` 里出不来。
2. **"每条转移的满足情况"告诉你它为什么**不走。条件不满足 → 差在哪个数上一目了然。
3. **"顺序就是优先级"** 把一条隐含的约定变成了屏幕上看得见的事实。
4. **"已见过"清单**让你确认某条分支到底有没有被执行过 ——
   这比打断点快得多。

> **能观测，才能调。** 这句话在任何复杂系统里都成立 ——
> 所以 S14（对象池）里我会给性能加面板，S11（存档）里会把存档打印出来给你看。
> 这不是"额外功能"，这是让系统可维护的前提。

## 五、核心概念四：Enter / Exit 与优先级

**Enter / Exit 是"一次性"的钩子**，不是每帧都跑的：

```csharp
public override void Enter()
{
    guard.AttackTimer = guard.AttackWindup + guard.AttackRecover;
    guard.ShowTelegraph(0f);      // ← 进入攻击时亮预警圈
}

public override void Exit()
{
    guard.HideTelegraph();        // ← 不管怎么离开都要收尾
    guard.AttackCooldown = 0.45f;
}
```

**把"无论怎么离开都要做的事"放进 Exit**，比在每个转移上各写一遍可靠得多。
本站的攻击状态可能因为"后摇结束"正常离开，也可能因为"被石头砸晕"被强行打断 ——
两种情况都会走 `Exit()`，所以预警圈一定会被关掉。

**优先级就写在转移表的注册顺序里**：

```csharp
// Chase 这一组：Stun 写在最前面 = 眩晕能打断追击
Machine.AddTransition("Chase", "Attack", "进入攻击距离", () => ...);
Machine.AddTransition("Chase", "Stun",   "被石头砸中",   () => ...);
Machine.AddTransition("Chase", "Alert",  "丢失目标",     () => ...);
```

`StateMachine.EvaluateTransitions` 按注册顺序取**第一条满足的**。
把 `→ Stun` 写在前面，眩晕就能打断一切。

> 这是个很容易忘的约定。**如果你发现 AI "该被打断却没打断"，
> 先去检查转移表的顺序，而不是去查条件写得对不对。**

## 七、五条练习任务的提示

### ① 读懂守卫的 巡逻 → 警觉 → 追击 → 攻击 转移条件
**难度**：★
打开游戏，看着左上角面板，做这几件事：

1. 站在守卫前面不动 —— 看它怎么一路走到 `Attack`，注意每次转移**用了多久**。
2. 走进视野后马上躲到柱子后面 —— 看 `Chase → Alert` 是怎么触发的。
3. 把石头扔在远处 —— 看 `Patrol → Alert`（听到动静那条路，**不同于"看到"**）。

### ② 新增「眩晕」状态：被石头砸中后进入 2 秒
**难度**：★★★
状态已经实现了。**真正的练习是加一个新状态** —— 比如「搜索」：

要求：守卫丢失目标后，不是直接回巡逻，而是先在**最后看到你的位置附近**来回找 3 秒。

做法：
1. 在 `guard.tscn` 里给 `StateMachine` 加一个 `Node` 子节点，命名 `Search`，
   挂一个 `GuardSearchState.cs`；
2. 在 `Guard.BuildStateMachine()` 里加两条转移：
   `Chase → Search`（丢失目标）和 `Search → Patrol`（搜索时间到）；
3. **别忘了把原来的 `Chase → Alert` 改掉** —— 否则新状态永远不会被进入。
   （这就是"表"的好处：你能一眼看出哪条路被抢了。）

### ③ 给状态加 OnEnter/OnExit，进入攻击时播放特效
**难度**：★★
现有实现用 `ShowTelegraph()` 画了一个不断扩张的红圈。练习：

1. **把 `Exit()` 里的 `HideTelegraph()` 删掉**，然后打晕守卫 ——
   你会发现预警圈**一直留在屏幕上**。
   **这就是"忘记在 Exit 里收尾"的典型症状：状态已经走了，表现还在。**
2. 加一个"进入 Chase 时屏幕边缘泛红"的效果，同样记得在 Exit 里关掉。
3. 给每个状态加一个不同的音效，注意 `Stun` 被打断时会不会重复播放。

### ④ 把转移条件抽成一张表，比较改起来是不是更容易
**难度**：★★
已经做了。**但真正的对比要做这件事**：

试着把 S02 的 `PlatformerPlayer` 也改成状态机驱动（Idle / Run / Jump / Fall / Dash）。
改完回答：

- 改之前，`_PhysicsProcess` 里有多少个 if？
- 改成状态机之后，加一个"滑墙"状态需要改几个文件？
- **代价是什么？**（提示：状态多了之后，"这个状态下能不能冲刺"这种跨状态约束
  会变得难写。状态机不是银弹 —— 它的代价是**把隐式的复杂度变成了显式的文件数量**。）

### ⑤ 思考：追击与受伤同时发生时，优先级该怎么定？
**难度**：★★
本站的答案是：**眩晕能打断追击、也能打断攻击**（转移表里 `→ Stun` 写在前面）。

练习：
1. 把 `Chase → Stun` 那条转移到 `Chase → Attack` **后面**，
   然后走进攻击距离的同时扔石头 —— 你会发现**攻击优先了，眩晕被吞掉**。
   **同一个输入，只改了一行的位置，行为完全变了。这就是"优先级"的实感。**
2. 回答：什么情况下"受伤优先"是对的？什么情况下"攻击优先"是对的？
   （提示：手感上，玩家会认为"我打中了它就该有反应" ——
   所以**玩家的动作**通常要高优先级；而 AI 自己的行为之间可以按情境取舍。）
3. 想一想：如果有 20 个状态、50 条转移，这个表格还看得过来吗？
   那时候该怎么办？（这就是"层级状态机"和"行为树"要解决的问题 —— S08 会碰到。）

## 八、常见坑速查

| 现象 | 原因 |
|---|---|
| 状态逻辑每帧跑两遍，时间相关行为快一倍 | 状态节点自己的 `_Process` 没关掉（`AddState` 里应该设 `ProcessMode = Disabled`） |
| 一帧内连跳好几个状态，中间特效漏播 | 转移求值后没 `return`。**一帧只走一步** |
| 该被打断却没被打断 | 转移表的注册顺序问题，不是条件写得不对 |
| 状态已经走了，特效还在 | 忘了在 `Exit()` 里收尾 |
| 进入某状态后永远出不来 | 那个状态没有注册任何出边，或者出边条件永远不满足 |
| 加了新状态但从来没被进入 | 被前面某条转移"抢"了（顺序问题），或者根本没有入边 |
| AI 偶尔慢一拍、行为不一致 | 感知和决策的执行顺序不确定。用 `ProcessPriority` 固定顺序 |
| 给 `PhysicsBody2D` 设负缩放来翻转朝向 | 碰撞形状计算会不可靠。**只翻外观节点，别碰物理体** |

## 九、通关后做什么

1. 回到第二节那段 if-else，试着用状态机把它重写一遍，**并且写出转移表**。
   然后回答：哪一部分状态机反而变麻烦了？
2. 把 `Guard.VisionHalfAngleDeg` 从 72 改成 180，再玩一次 ——
   你会发现"绕到背后"这个策略失效了。
   **AI 的难度很多时候只是"它知道多少"的问题，不是算法的问题。**
3. 打开 `F3` 性能面板，看守卫在 `Patrol` 和 `Chase` 时的帧时间有没有区别。
   （提示：几乎没有。**5 个状态的状态机开销可以忽略不计** ——
   所以不要因为"怕慢"而不敢用状态机。）
4. 想清楚一个问题：本站的守卫**只有 5 个状态**，但已经有 11 条转移了。
   如果是 20 个状态呢？去查一下「层级状态机（HFSM）」和「行为树（Behavior Tree）」，
   看看它们各自解决了状态机的哪个短板。
