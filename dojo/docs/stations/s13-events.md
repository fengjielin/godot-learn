# S13 · 事件总线

> **练什么**：Autoload 全局单例 · 信号 · 解耦 · **连接泄漏**
> **一句话**：事件总线用**「可追踪性」**换了**「可扩展性」** —— 知道这笔交易划不划算，比会用它更重要。
> **难度**：★★★☆☆（API 五分钟学会，难的是判断"这里该不该用"）

---

## 一、先玩一遍

场景里有两样东西：**金币**（走过去就捡）和**靶子**（按 `J` 打掉）。
后台有三个**互相不认识**的东西在工作：成就系统、飘字提示、统计面板。

| 按键 | 作用 |
|---|---|
| `1` | 在**事件总线**和**直接调用**两种写法之间切换 |
| `2` | 制造一次**悬空连接**错误（会捕获给你看） |
| `J` | 打靶子 |

两种写法的**效果完全一样**，差别只在"谁认识谁"。

## 二、核心概念一：两种写法的形状

**事件总线**（本站默认）：

```csharp
// Pickup.cs —— 金币不知道有成就系统，也不知道有统计面板
EventBus.Instance.EmitSignal(EventBus.SignalName.ItemPickedUp, ItemId, Amount);
```

**直接调用**（按 `1` 切换）：

```csharp
// Pickup.cs —— 金币必须持有接收方的引用，接收方还得暴露一个公开方法
_DirectReceiver.OnItemCollected(ItemId, Amount);
```

**差别不在写法长短，在于加一个新功能时要改几处。**

| | 事件总线 | 直接调用 |
|---|---|---|
| 加一个成就 | **一行已有代码都不用改**，加个订阅就行 | 要去改金币里那段 if |
| 加十个成就 | 还是不用改 | 那段 if 有十个分支 |
| 想知道"谁触发了它" | ❌ 打开 `Pickup.cs` **看不到**，只能全局搜索事件名 | ✅ 顺着调用栈一路可见 |
| 调试断点 | 断在事件上，看不出是谁发的 | 断在调用处，一目了然 |
| 执行顺序 | 由订阅顺序决定，容易出玄学 bug | 确定 |
| 出错的后果 | 一个订阅者抛异常，**后面的订阅者全都不执行** | 直接崩在你面前，位置明确 |

### ★ 结论（这一站唯一要记住的）

> **核心流程用直接调用，横切关注点（成就 / 统计 / 音效 / 提示 / 埋点）才用事件。**

"玩家攻击敌人"是核心流程 —— 看得见、追得到、必须确定。
"解锁了一个成就"是横切关注点 —— 谁在乎都行、加多少个都行、顺序无所谓。

**把核心流程也塞进事件总线，你会得到一个"能跑但没法调试"的项目。**

## 三、核心概念二：连接泄漏（本站会亲手撞一次）

按 `2` 会做这件事：

1. 造一个临时节点，让它订阅 `EventBus.NoticeCSharp`（**普通 C# event**）
2. `QueueFree()` 销毁它，**故意不退订**
3. 再发一次事件

实测捕获到的异常：

```
ObjectDisposedException：Cannot access a disposed object.
Object name: 'Godot.Node'.
```

**换成 Godot 信号（`Notice`）就什么都不会发生** —— 引擎在任一端被释放时会**自动清理连接**。

| | Godot 信号 | 普通 C# event |
|---|---|---|
| 订阅者被释放 | 引擎**自动断开** | ❌ 委托还留在调用列表里 |
| 忘记退订的后果 | 无 | 下次触发时抛 `ObjectDisposedException` |
| 谁负责清理 | 引擎 | **你** |

### 三种"退订"写法，按推荐程度

```csharp
// ① 最推荐：Godot 信号 —— 引擎兜底
bus.ItemPickedUp += OnPickup;

// ② 用 C# event 就必须写配对的生命周期方法
public override void _Ready()    => bus.Notice += OnNotice;
public override void _ExitTree() => bus.Notice -= OnNotice;   // ← 漏了这行就是 bug

// ③ 一次性订阅用 lambda 时，一定要把返回的 Callable 存下来
//    否则你没法退订（每次 -- 都生成新对象）
```

⚠️ 顺带一个语言细节：`event` 关键字只允许在**声明它的类型内部**赋值。
所以外面不能写 `bus.NoticeCSharp = null;` —— **事件的拥有者必须自己提供清理方法**
（本站是 `EventBus.ClearCSharpSubscribers()`）。
这是语言在提醒你：**事件的拥有者要为"清理"负责，因为它没法指望别人记得退订。**

## 四、核心概念三：为什么 EventBus 是 Autoload

```csharp
public partial class EventBus : Node
{
    public static EventBus Instance { get; private set; } = null!;
    public override void _Ready() => Instance = this;
}
```

`EventBus` 挂在 `project.godot` 的 `[autoload]` 里，**先于所有场景加载，且永不被释放**。

- ✅ 任何节点在任何时候都能找到它，不需要互相持有引用
- ✅ 只有一个，不存在"两个总线"的问题
- ⚠️ **它是个全局单例**。挂在上面的每一个信号都是**隐式依赖** ——
  你看某个类的构造函数，看不出它依赖事件总线，但它就是依赖。
  **全局单例用着方便，代价是"这个类到底需要什么"变得不可见。**

**如果想减轻这一点**：把所有信号集中声明在 `EventBus` 里（本站就是这么做的），
让它成为一份**可读的事件目录**。打开这个文件就知道游戏里有哪些事件 ——
这比"信号散落在各个场景的各个节点上"好得多。

## 六、五条练习任务的提示

### ① 新增一个事件，让成就系统弹出提示
**难度**：★★ 已经做了（本站有 4 个成就）。练习：

1. 在 `EventBus` 里加一个 `PlayerJumped` 信号，让成就系统订阅它并解锁"跳跃 10 次"。
   **注意：你完全不用碰玩家脚本以外的东西 —— 但那个"以外"里包含哪些文件？数一数。**
2. 加一个"连击"事件：3 秒内击杀两次才算。回答：
   **这个计时状态该放在发事件的一侧，还是收事件的一侧？**
   （提示：放在消费者侧。**发送方只负责"报告发生了什么"，不负责"这意味着什么"。**）

### ② 把本站里的直接函数调用改成走事件总线，对比两种写法
**难度**：★★★ 已经做了（按 `1` 切换）。练习：

1. 切到"直接调用"模式，然后**试着加一个新成就**。
   你会发现必须去改 `Pickup.cs` 或 `AchievementSystem` 的公开接口 —— 这就是耦合。
2. 切回事件总线，加同样的成就 —— **一行已有代码都不用改**。
3. **回答**：既然事件总线这么好，为什么本站的"打靶子"用的是 `EmitSignal` 而
   `Pickup.Collected` 用的是普通 C# event？
   （提示：`Collected` 只给**站台自己**听，没有第三方。**只关心自己人的通知，不需要广播。**）

### ③ 故意不断开连接然后销毁发送方，观察报错
**难度**：★★★ 已经做了（按 `2`）。练习：

1. 把 `StepDanglingDemo` 里的 `ClearCSharpSubscribers()` 注释掉，
   然后继续玩 —— 你会发现**每次发消息都抛一次异常**，
   而且**后面的订阅者全都不执行**了（飘字提示直接消失）。
   **这就是"一个坏订阅者毒死整条链路"。**
2. 改成 Godot 信号（`Notice`）再做一次同样的实验 —— **什么都不会发生**。
3. **回答**：如果非要用 C# event，怎么保证不会忘？
   （提示：把 `+=` 和 `-=` 写在同一个文件的相邻两行，并且**用 `_Ready` / `_ExitTree` 配对**。
   本站的 `AchievementSystem` 就是这么做的 —— 去看一眼那个文件的结构。）

### ④ 加「本局统计」面板：击杀数、拾取数、移动距离
**难度**：★★ 已经做了。练习：

1. 现在统计是站台自己算的（移动距离）。改成**发一个 `PlayerMoved` 事件**，
   由统计系统订阅计算。回答：**这样做更好了还是更糟了？为什么？**
   （提示：每帧发一个事件 = 每帧一次委托调用 + 参数装箱。
   **高频的东西不要走事件总线** —— 事件是给"离散的、有意义的时刻"用的。）
2. 让统计能在**切场景后保留**（提示：`SaveSystem` 已经是 Autoload 了，用 `user://`）。
   **这一步就跨到 S11 存档站了。**

### ⑤ 思考：什么时候不该用事件总线？
**难度**：★★★
用第二节那张表回答这几个具体问题：

1. **伤害计算**该走事件吗？（提示：不该。**顺序敏感 + 需要明确返回值**。）
2. **UI 刷新**该走事件吗？（提示：该。UI 是最典型的横切关注点。）
3. **玩家死亡**该走事件吗？（提示：该 —— 而且这正是它的价值：
   死亡要触发音效、动画、成就、存档、重开菜单……**让发送方去认识这五个系统是灾难**。）
4. **每帧的位置同步**呢？（提示：绝对不该。高频 + 无意义。）
5. 最后一题：**如果你发现某个事件只有唯一一个订阅者，它还需要走总线吗？**
   （提示：通常不需要。**为一个订阅者付"可追踪性"的代价不划算** ——
   直接调用，等第二个订阅者出现时再改。这也是"不要过早抽象"的一个具体例子。）

## 七、常见坑速查

| 现象 | 原因 |
|---|---|
| `ObjectDisposedException` | 用了 C# event 却忘了 `-=`。**Godot 信号不会这样** |
| 一个订阅者抛异常，其他订阅者不执行 | 信号是同步广播。**要么每个订阅者自己 try/catch，要么别让它抛** |
| 事件的执行顺序变成玄学 | 由订阅顺序决定。**不要依赖顺序**，或者干脆不用事件 |
| 找不到是谁发的这个事件 | 这就是事件总线的固有代价。**核心流程别用它** |
| 每帧发事件导致卡顿 | 高频的东西不该走总线。离散的"时刻"才适合 |
| 切场景后事件没了 / 重复订阅 | 连接建在场景里的节点上，场景一换就断。Autoload 上的连接才是长期的 |
| 外面写 `bus.MyEvent = null` 编译不过 | `event` 只能在声明类型内部赋值。**让 EventBus 自己提供清理方法** |

## 八、通关后做什么

1. **数一数**：打开 `EventBus.cs`，看看现在有几个信号。
   然后找出**每一个信号分别有几个订阅者**。
   只有 1 个订阅者的那些 —— 它们真的需要走总线吗？
2. 想清楚 `EventBus.Instance` 这个静态单例：
   **如果游戏以后要支持"本地双人"，一个全局总线还够用吗？**
   （提示：两个玩家的 `PlayerDamaged` 会混在一起。这时候需要什么？）
3. **跨站练习**：S16 的状态效果容器是挂在角色身上的组件，
   现在它靠**直接调用**（`DamageTick?.Invoke`）通知外面。
   改成走事件总线，然后回答：**变好了吗？**
   （提示：如果状态效果只有玩家和敌人两种宿主，直接调用就够了。）
4. 去 `docs/00-学习路线图.md` 看一眼自检清单里 S13 那条，确认你能答上来。
